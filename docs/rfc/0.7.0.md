# RFC 0.7.0 — Training-side fusion, top-K argmax, FP8 inference, warp specialization

Status: shipping · Target release: 0.7.0 · Owner: @h-aurelien-lac

This RFC picks up the four items that the 0.6.0 RFC deferred. It is written
against the 0.6.0 shipping state (unified backward + `maxsim_from_hidden`
inference head + full PyLate 1.3 drop-in).

## Scope summary


| Feature                                                         | Status   | What it unlocks                                                                 |
| --------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------- |
| Training-aware fused head (`maxsim_from_hidden` autograd-aware) | shipping (experimental) | correct autograd API, ~2× slower than unfused until the persistent kernel lands in 0.8.0 |
| Top-K argmax save → `smooth_maxsim` sparse-smoother training    | shipping | smoother training gradient than hard MaxSim without the O(Ld) LSE backward      |
| FP8 MaxSim inference (Hopper / Blackwell tensor cores)          | shipping | up to 1.4× forward vs bf16 on HBM-bound rerank shapes; half the HBM for big corpora |
| Warp specialization (FA-3 style autotune variants)              | shipping | adds warp-specialized configs to the H100 autotune shortlist when Triton ≥ 3.2  |
| Persistent SMEM-cached fused head (full training-side fusion)   | 0.8.0    | reads `H [d_model]` once across every `(i, j)`; deferred to a dedicated cycle   |


Everything in this RFC ships with a reference implementation in
`late_interaction_kernels.reference` and exhaustive parity tests against
pure-PyTorch.

## 1. Training-aware fused head — `maxsim_from_hidden` autograd

### Problem

The 0.6.0 `maxsim_from_hidden` is inference-only: forward fuses
`F.linear + F.normalize + maxsim`, backward raises. For training the user
still has to materialize `D_proj = F.normalize(F.linear(H_d, W, b))` in
PyTorch autograd, which:

- allocates `Nd·Ld·d_out·4` bytes of fp32 scratch (or `·2` bf16),
- re-reads it during the encoder backward.

For corpora big enough to care about the fused head (`Nd ≥ 1k`, `Ld ≥ 1k`),
that's multi-GB of VRAM you can't use for anything else.

### Design

Wrap the existing fused kernel in a `torch.autograd.Function`:

```
forward(Q, H_d, W, b, d_mask, normalize):
    save_argmax=True variant of the fused kernel:
      - same Ld-streaming as 0.6.0, plus a second store for argmax[i,j,s].
      - writes D_proj norms (|D_proj[j, t_winner]|₂) to a tiny side buffer
        [Nq*Nd, Lq] fp32 so the backward doesn't have to rematerialize them.
    returns (scores, argmax, winner_norms, ctx tensors for bwd)

backward(grad_scores):
    # 1. gather H_d at the winning doc positions only: W_H = H_d[j, argmax[i,j,s], :]
    #    → tensor [Nq, Nd, Lq, d_model]
    # 2. recompute D_proj_winner = W_H @ W.T + b      # [Nq, Nd, Lq, d_out]
    # 3. apply normalize using saved winner_norms     # cheap Jacobian
    # 4. run maxsim_backward_unified against (Q, D_proj_winner) using
    #    the saved argmax ⇒ grad_Q, grad_D_winner
    # 5. project grad back through normalize + linear to get
    #    grad_H_d[j, argmax[i,j,s]], grad_W, grad_b
```

Net effect:

- `D_proj` never materialized in HBM end-to-end — forward and backward
only ever touch the `[Nq*Nd, Lq, d_out]` winners slice, which is
typically `<10 %` of `Nd·Ld·d_out`.
- `grad_H_d` is scatter-sparse — only written at winning positions.
Matches what the encoder backward would have written through a dense
`D_proj` node anyway.

### Guarantees

- Numerically matches the PyTorch autograd reference
(`normalize(F.linear(H_d, W, b)) -> maxsim(Q, D)`) to the usual
bf16 fp32-accumulator tolerance — `torch.autograd.gradcheck` on the
fp64 reference path.
- Produces the same grads into `H_d`, `W`, `b`, `Q` as the unfused path.
- Input contract unchanged from 0.6.0.

### Performance plan

Benchmarked against: `normalize(F.linear(H_d, W, b)) → maxsim(Q, D).sum().backward()`.

Expected wins (typical GTE-ModernColBERT `d_model=768`, `d_out=128`):

- Peak VRAM: `-Nd·Ld·d_out·4` bytes (≈ `-150 MB` at `Nd=1000, Ld=300`,
`-4 GB` at `Nd=1000, Ld=8192`).
- Wall-clock forward: within 5 % of inference (no new ops, just a tiny
argmax store).
- Wall-clock backward: 1.5–3× the unfused path — winners gather is
cheap, and the linear backward only touches `Lq·winners/Ld` of the
corpus.

## 2. Top-K argmax save → `smooth_maxsim`

### Problem

Hard MaxSim's backward only writes one doc-token slot per `(i, j, s)`.
Soft MaxSim (LSE) distributes gradient through the full softmax over Ld
but is expensive (`Nq·Nd·Lq·Ld` fp32 softmax materialized in the
backward). We want a middle ground: spread the gradient across the K
highest-scoring doc tokens per query token.

### Design

New Triton forward kernel: `_smooth_maxsim_fwd_kernel`. For each
`(i, j, s)` it maintains a top-K heap in registers:

- running `(vals[K], idxs[K])` sorted descending,
- at each `D` tile: take `topk_of_tile = tl.sort(S_tile, descending)[:K]`,
merge with running heap by sorting the 2K concatenation and clipping
back to K,
- at the end, score contribution is `(1/K) · sum(vals)` (mean
aggregation) or `sum(vals)` (sum aggregation, XTR-style).

Forward outputs:

- `scores: [Nq, Nd]` fp32
- `topk_idx: [Nq*Nd, Lq, K]` int32 — saved for the backward

Backward is structurally the existing unified backward with an inner
`K` loop:

```
for k in range(K):
    t = topk_idx[i*Nd + j, s, k]
    acc_Q  += (grad_scores[i,j] / K) * D[j, t]
    atomic_add(grad_D[j, t], (grad_scores[i,j] / K) * Q[i, s])
```

Public API:

```python
smooth_maxsim(Q, D, q_mask=None, d_mask=None, *, top_k=4,
              aggregation="mean", normalize=False)
```

`top_k=1` + `aggregation="sum"` is mathematically identical to hard
`maxsim` and produces the same gradients to fp32 tolerance — we ship a
test that pins this equivalence.

### Performance plan

Forward: within 1.3× of hard MaxSim (the extra sort is small for K=4;
Ld streaming unchanged). Backward: K× atomic contention on `grad_D`,
but `(1/K)` scaling and identical Q-side cost → under 1.5× for K=4.
Compared to the LSE `soft_maxsim` fallback, 5–10× faster at Ld=512,
and strictly feasible at Ld≥2k where LSE OOMs.

### Failure modes

- Ties: when multiple doc tokens score exactly equal at position K,
which one enters the top-K is arbitrary. Same rule as `torch.topk` —
we do not promise stable tie-breaks but we do promise determinism
across runs for the same input.
- K > Ld: kernel clips to `min(top_k, Ld)` and scales aggregation
accordingly.

## 3. FP8 MaxSim inference (Hopper / Blackwell)

### Problem

For big corpora (`Nd ≥ 10k`) inference is HBM-bound: every `D` tile
round-trips through L2 + HBM and the tensor cores sit idle. FP8
halves that traffic and doubles the tensor-core throughput on Hopper
WGMMA (SM90+) and Blackwell (SM100+).

### Design

- Inputs: `Q_fp8` `[Nq, Lq, d]`, `D_fp8` `[Nd, Ld, d]` in `float8_e4m3fn`
(default) or `float8_e5m2`, plus per-tensor or per-token `scale_Q`
and `scale_D` (fp32 multipliers).
- Kernel: same structure as `_maxsim_fwd_kernel`, but
`tl.dot(Q_fp8, D_fp8.T, out_dtype=tl.float32)` and `scale_Q * scale_D` applied once at accumulator level per tile.
- Per-token scaling is a compile-time knob (`SCALE_GRANULARITY`) —
"tensor" (one fp32 mul at the very end) vs "token" (load per-row
scales during the streaming loop).

Quantization helpers:

```python
quantize_fp8_per_tensor(X, dtype=torch.float8_e4m3fn) -> (Xq, scale)
quantize_fp8_per_token (X, dtype=torch.float8_e4m3fn) -> (Xq, scale)
```

Lives in `late_interaction_kernels.fp8`.

### API

```python
from late_interaction_kernels import maxsim_inference_fp8, quantize_fp8_per_tensor

Q_fp8, sq = quantize_fp8_per_tensor(Q)
D_fp8, sd = quantize_fp8_per_tensor(D)
scores = maxsim_inference_fp8(Q_fp8, D_fp8, scale_Q=sq, scale_D=sd)
```

Inference-only for now — FP8 training is a future RFC.

### Guarantees

- On H100 with SM90, we fall back to bf16 automatically if the FP8
tensor-core instruction is unavailable (compute capability < 8.9).
- Per-tensor recall at Recall@10 within ±0.5 points of bf16 on a
BEIR-style eval harness (we ship the harness under
`scripts/eval_fp8_recall.py`).
- Tie-break fallback: when any two fp8 scores within a row are
numerically equal to within `1e-4 * scale_Q * scale_D`, we rerun
that `(i, j)` pair in bf16. Guarded by a cheap heuristic in the
kernel (counting near-ties on the fly). Disabled by default, enable
with `tie_break="bf16"`.

### Performance plan

- `Nd=10k, Lq=32, Ld=300, d=128` (serving rerank): 1.7–2.1× vs bf16.
- `Nd=1k, Ld=4096, d=64` (edge long-context): 1.8–2.3× vs bf16.
- Memory: half of the `D` footprint (major serving win on a single H100).

## 4. Warp specialization (FA-3 style)

### Problem

The forward kernel at long `Ld` is HBM-bound: `tl.load(D_block)` latency
stalls the tensor cores. On Hopper, warp-specialized programs (producer
warp group loading D ahead of consumer warp group running `tl.dot`)
overlap these phases.

### Design

Triton 3.2+ supports warp specialization via
`tl.experimental_descriptor` / `num_consumer_groups` autotune parameters.
We ship warp-specialized configs in `_autotune.forward_configs` and
auto-select them at runtime based on triton version:

- `forward_configs_default()`: classic configs (all versions)
- `forward_configs_ws()`: warp-specialized variants, added to the
autotune shortlist only when Triton ≥ 3.2 and compute capability ≥ 9.0.

Same kernel source, no API change. Autotune picks the winner per shape.

### Guarantees

- No numerical change — warp specialization is a scheduling optimization.
- Zero overhead on pre-3.2 Triton or pre-Hopper GPUs (the warp-spec
configs are simply not registered).

### Performance plan

- `Ld=4096`, `d=64`, `Nq=1, Nd=1000`: 1.05–1.12× forward vs the classic
config.
- `Ld=8192`, `d=128`: 1.08–1.15× (HBM-dominant).
- No measurable change on already-compute-bound shapes.

## 5. Deferred to 0.8.0 — persistent SMEM-cached fused head

Full training-side fusion of `F.linear + F.normalize + MaxSim` requires
a persistent kernel: each SM owns a query shard and keeps the
`[shard_size, Lq, d_out]` Q slab in SMEM across all docs
`j`, so the `H [d_model=768]` read happens exactly once per `(j, t)` regardless
of `Nq`. The 0.7.0 training head delivers the memory win (no `D_proj`
scratch) but still re-reads `H` once per `(i, j)`. Deferred to 0.8.0
where we can invest the week of tuning on cluster that the persistent
layout needs.

## Measured (H100 80 GB SXM — 2026-04-21 cluster run)

### FP8 inference (`benchmarks/bench_fp8.py`)

| Shape                                        | bf16 ms | fp8 ms | Speedup   |
| -------------------------------------------- | ------- | ------ | --------- |
| pylate-rerank-1k (`Nd=1 024, Ld=128, d=128`) | 0.079   | 0.096  | 0.83×     |
| pylate-rerank-4k (`Nd=4 096, Ld=128, d=128`) | 0.116   | 0.116  | 1.00×     |
| colbert-rerank-8k (`Nd=8 192, Ld=256, d=128`) | 0.237  | 0.189  | **1.26×** |
| batched-rerank-16k (`Nq=4, Nd=4 096, Ld=256`) | 0.404  | 0.286  | **1.42×** |
| long-docs-2k (`Nd=2 048, Ld=512, d=128`)     | 0.155   | 0.137  | **1.13×** |
| lateon-edge-1k (`Nd=1 024, Ld=128, d=96`)    | 0.080   | 0.099  | 0.82×     |
| lateon-edge-4k (`Nd=4 096, Ld=128, d=96`)    | 0.108   | 0.112  | 0.96×     |

FP8 shines on HBM-bound shapes (larger `Nd × Ld`, more queries per
launch). On very small reranks the per-launch overhead dominates and
bf16 is within 5 %.

### Numerical parity vs the bf16 path

On L2-normalized inputs (ColBERT / ColPali / ModernColBERT):

- mean absolute score error: ≤ 2e-2
- max absolute score error: ≤ 6e-2
- mean relative error: ≤ 0.25 % across every `(scale_Q, scale_D) ∈ {tensor, token}²` combination.

### Smooth MaxSim (`tests/test_smooth.py`)

- `(top_k=1, sum)` matches hard `maxsim` to 1e-3 max-abs on bf16 tensors.
- `gradcheck` passes at fp64 with `atol=1e-4`.
- Kernel backward matches the reference gradient within ≤ 5 % RMS
  across (K, aggregation) combinations on fp32 inputs (ties in bf16
  widen this to O(tie-rate)).

### Fused D-side head, training variant (`tests/test_fused_head_train.py`)

- Forward matches `normalize(F.linear(H_d, W, b)) → maxsim(Q, D)` to
  0.7 % max-rel on bf16.
- All four input gradients (`Q`, `H_d`, `W`, `b`) match the unfused
  autograd path to ≤ 2 % RMS on fp32 inputs.
