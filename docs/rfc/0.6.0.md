# RFC — 0.6.0 performance track

This RFC scopes the performance-oriented work for 0.6.x. The target is
concrete: **2-3× training throughput** on MaxSim-heavy workloads and
**2-3× single-query inference throughput** at large `Nd`. We ship this
in small, validatable increments rather than one big-bang release.

## Current state (0.5.1)

- Forward: FlashAttention-style tiles, autotuned on H100 / A100 / Ada /
  Ampere. Competitive with `flash-maxsim` (IBM); not verified head-to-head
  yet — see `benchmarks/bench_flash_maxsim.py` (new in this release).
- Backward: two separate kernels, `grad_Q` (row-owned) and `grad_D`
  (`atomic_add` or CSR-deterministic).
- Varlen / residual / soft-maxsim: all autograd-aware.
- Weakest spots we know about:
  - Two-pass backward re-reads Q, D, dScores from HBM → kernel is
    bandwidth-bound at long sequences.
  - `soft_maxsim` backward is a pure-PyTorch recompute of the
    `[Nq, Nd, Lq, Ld]` softmax — fine at `Ld ≤ 512`, expensive past that.
  - Inference path still requires the caller to materialize a
    `[Nd, Ld, d_out]` `D_proj` tensor when the on-disk format is
    `[Nd, Ld, d_model]` hidden states → multi-GB HBM scratch for large
    corpora.
  - Training with packed tensors works but needs BYO collator + encoder
    adapter (documented in `docs/packed_training.md`).

## Milestones

### 0.6.0 — Land the foundations

**In scope**

1. `maxsim_from_hidden` — fused projection + normalize + MaxSim for the
   D-side. Inference-focused (where the materialization-avoidance win is
   unambiguous). Forward only; no backward in 0.6.0.
2. Top-K argmax save for `soft_maxsim` backward. The forward already
   runs in Triton; only the backward is slow. With a `top_k` hyper­parameter
   we cap the backward recompute cost at `O(Nq·Nd·Lq·K)` instead of
   `O(Nq·Nd·Lq·Ld)`, for any `Ld`.
3. Head-to-head benchmark vs `flash-maxsim` (roipony) so we can report
   parity or superiority with real numbers instead of hand-waving.
4. Unified-backward reference implementation (pure PyTorch) and a
   scaffold for the Triton kernel. The reference establishes numerical
   parity; the kernel lands in 0.6.1 once the cluster autotune shortlist
   is settled.

**Out of scope (deferred to 0.6.x)**

- Unified dQ+dD Triton kernel implementation → 0.6.1.
- Persistent kernel + SMEM-cached fused head for training → 0.7.0.
- FP8 path → 0.7.0 (depends on numerical-stability validation harness).
- Warp specialization (Flash-Attn-3 style) → 0.7.0 (Triton 3.2+).

### 0.6.1 — Unified backward kernel (FA-2 style)

Single-pass `grad_Q` + `grad_D` kernel. Shares the Q, D, dScores reads
between both accumulations. Expected: **2× backward throughput** on
MaxSim-dominant shapes (long `Ld`, high `Nd`).

Validation:
- Numerical parity against the 0.6.0 reference impl (tight tolerances
  on bf16 / fp16, `gradcheck` on fp64 reference).
- Autotune sweep on H100 (32 configs × 4 shape buckets = 128 runs,
  cached into `_autotune.py`).
- End-to-end training wall-clock on PyLate MSMARCO + LateOn-Code-edge.

### 0.7.0 — FP8 path + persistent fused head

Two big wins that share a validation harness.

- **FP8** (Hopper WGMMA + Blackwell): `Q, D ∈ fp8_e4m3fn`, accumulator
  fp32, per-token scaling for `max` stability. Expected: **1.5-2×
  forward**, **1.3-1.5× backward** on H100 once numerics are validated.
  Ship as opt-in (`dtype=torch.float8_e4m3fn`) with an automatic
  fallback to bf16 on score-tie detection.
- **Persistent kernel + SMEM-cached fused head for training**: one
  kernel per SM, picks a `q_idx` from a work queue, projects +
  normalizes the query once into SMEM, then iterates over all
  `d_idx` in the batch that need scoring. Removes the 6× HBM
  amplification the naive training-side fused head suffers from.
  Expected: **10-20% end-to-end training speedup** on
  ModernColBERT-sized models (encoder still dominates).

### 0.8.0 — Inference-engine-grade kernels

- Persistent kernel + split-K for small-`Nq` × big-`Nd` inference.
  Expected: **2-3× rerank throughput** on 1-query × 10k-100k docs.
- Int8 dense path (per-token scale). Expected: **3-4× forward** vs
  fp16 on Hopper int8 tensor cores.
- Hierarchical MaxSim (PLAID approx + residual rerank in one kernel).

## HBM analysis — why the naive training-side fused head is a trap

Pre-fused training step, B=32, Lq=32, Ld=200, d_model=768, d_out=128,
bf16:

| Step                        | HBM reads                      | HBM writes                |
| --------------------------- | ------------------------------ | ------------------------- |
| Encoder → H                 | (upstream)                     | 2·B·L·d_model ≈ 20 MB     |
| Linear: H @ Wᵀ              | 2·B·L·d_model ≈ 20 MB          | 2·B·L·d_out  ≈ 3 MB       |
| F.normalize                 | 2·B·L·d_out  ≈ 3 MB            | 2·B·L·d_out  ≈ 3 MB       |
| MaxSim forward              | Nq·Nd·(Lq+Ld)·d_out ≈ 60 MB    | Nq·Nd ·4 ≈ 4 KB           |
| **Total**                   | **~83 MB**                     | **~26 MB**                |

Naive fused head (Linear + normalize + MaxSim in one kernel), same
shapes:

| Step                              | HBM reads                          |
| --------------------------------- | ---------------------------------- |
| MaxSim-from-hidden forward        | Nq·Nd·(Lq+Ld)·d_model ≈ **360 MB** |

Reads are **4× worse**. The only way to reclaim this is a persistent
kernel that projects H → Q once per query and keeps Q in SMEM across
all (i, j) pairs that share the same `i`. That's a bigger project and
lands in 0.7.0.

The 0.6.0 `maxsim_from_hidden` is therefore scoped to **inference**
where `Nq=1` (or small) and the pre-projected `D_proj` matrix would
otherwise be the HBM hog:

| Config                                        | `D_proj` scratch if pre-projected |
| --------------------------------------------- | --------------------------------- |
| Nd=10k, Ld=300, d_out=128, bf16               | **768 MB**                        |
| Nd=100k, Ld=180, d_out=128, bf16              | **4.4 GB**                        |
| Nd=1M, Ld=256, d_out=96, bf16 (LateOn-edge)   | **46 GB** (OOM)                   |

Fusing D-side projection into MaxSim makes those corpora runnable
without staging `D_proj`.

## Non-goals

- We do not compete with fast-plaid / ColBERTv2 on end-to-end search
  engine functionality (IVF probe, on-disk index, query planning). This
  library stays a set of fused kernels callable from Python.
- We do not plan to support non-CUDA backends (ROCm, MPS) in 0.6.x.
  The reference implementations remain CPU-runnable for correctness.
